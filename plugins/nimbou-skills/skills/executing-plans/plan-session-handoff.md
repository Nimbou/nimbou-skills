# Planner subagent and execution task handoff

This handoff applies when `nuxt-plan`, `nestjs-plan`, `laravel-plan`, or the small-plan path of `change-plan` is invoked. The current task remains the controller for planning and task creation.

1. Resolve the target project's absolute checkout and a unique feature slug. Unless the user chose a different path, reserve `docs/plans/<slug>/doc.md` inside that project. Reuse an existing plan directory only when it is for the same feature; do not overwrite an unrelated `doc.md`.
2. Dispatch one planning subagent with `spawn_agent`, `model: gpt-6-sol`, `reasoning_effort: medium`, and `fork_turns: "none"`. Give it a self-contained brief: the target checkout, this planner skill and any approved design/contract artifacts, the exact plan path, the user's scope and verification preferences, and the instruction to follow the planner's technical rules. The worker writes and self-reviews the plan, then reports the path, closed decisions, checks, and blockers. It does not dispatch another planner, create a Codex task, or implement code. If this file is read by the planning worker, perform the planning directly; do not redispatch.
3. The controller checks that the plan exists in the target checkout, contains `## Ondas de Execução`, meets the planner's self-review, and is ready for `executing-plans`. Resolve any mechanical gap with the worker or repository evidence. If a required design or business decision is missing, keep the plan and report the blocker; do not start execution.
4. This requested workflow authorizes execution after the plan passes review unless the user explicitly asked for planning only. Use `list_projects` to identify the saved target project, then `create_thread` with `model: gpt-6-luna`, `thinking: max`, and a project worktree. Use `startingState: { type: "working-tree" }` so the new checkout includes the just-written plan and other current changes. Give the new task the absolute source checkout, relative plan path, intended feature, and this instruction: verify that the plan exists in its new checkout, run `nimbou-skills:executing-plans` there, and report any missing plan or incompatible starting state before writing code. Carry forward the user's explicit authorization or restriction on multi-agent execution; task creation alone does not grant permission for implementer subagents. Do not execute the plan in the planning task.
5. Return the plan path and created task identifier. If the user asked only for a plan, or the saved project/worktree or task creation is unavailable, return the plan and the concrete reason no execution task was started. Do not silently execute in the current task.

The Luna/max setting is for the execution task's controller. When that task has explicit multi-agent authorization, `executing-plans` still chooses implementation and review workers under its own model policy, normally Sol/medium for behavioral work. The controller and workers must not assume that a nested agent gains additional capacity.
